# 固定目标与优化边界

## 交付目标

专门优化 2 × NVIDIA A100-SXM4-80GB、单机 TP=2，运行业务所称 Qwen3.8-27B 的指定 LoRA 合并后 FP8 checkpoint。模型架构按该 checkpoint 的实际 config 校验，当前为 qwen3_5。MTP 必须使用这份完整模型中经过验证的权重。

交付目标是在真实识图工作负载中，以相同业务质量，显著降低端到端延迟并提高实际并发吞吐，超过同机、同模型的 vLLM MTP。仅一个算子更快、原生内部基线更快或一张图片上更快，都不足以证明目标达成。

FP8 指 checkpoint 权重格式。当前 A100 执行路径使用 W8A16、BF16 计算和 FP32 GDN 状态；BF16 解码缓存是实现选择，不改变原始权重来源。LoRA 在线热切换与动态适配器执行不属于交付范围。

## 范围取舍

- TP1、TP4、K16、随机小模型及 eager 路径保留为数值验证或诊断手段；不把它们作为产品优化目标。
- 不扩大到其他模型、其他 GPU、通用模型插件、通用调度框架或多机集群。
- 现有 HTTP、采样及缓存功能保留，新的性能投入优先用于 TP2 固定模型关键路径。
- 图片分辨率、图片数、提示词与输出长度按实际业务分布分桶，不能为了加速而改变模型需要的预处理或缩小图片。
- 实验开关用于消融。只有经过数值、业务质量及性能验证的组合才能成为固定部署配置。

## 当前偏离与缺口

1. 工程说明仍突出 TP1/2/4 和多种实验路径，专用交付边界不够明确。
2. 层执行仍在运行期读取 JSON、构造名称并查找权重；需逐步生成固定形状与固定指针的执行计划。
3. 识图前端仍依赖 Python 处理与文件 IPC，视觉网络也保留多次 ATen 调用；这些端到端开销不能靠文本解码优化消除。
4. 多请求 MTP 目前逐请求调用 speculate；原生非 MTP 的 decode_batch 不能代表 MTP 已批处理。
5. 最近结果只有一张业务图片、C1 的 vLLM 对照。C2 原生结果不能证明超越 vLLM 并发吞吐。
6. 当前 vLLM 对照关闭 prefix/MM 缓存，KV dtype 未显式设置线上 fp8。线上截图中的服务选项与当前冷请求基准并非完全相同，必须单独冻结并记录配置。
7. 原生与 vLLM 的坐标 24/23 分歧仍未定位。不能以速度改善替代质量验收。

## 优化优先级

1. 固定 TP2 执行计划：在导入/初始化阶段绑定权重、拓扑、精度、矩阵尺寸和缓冲布局，减少热路径解释与分配。
2. A100 与模型尺寸专用矩阵计算：针对实际 prefill、MTP 验证和词表头尺寸，选择共享权重 GEMV、Tensor Core GEMM 与缓存布局。只有实测更快的路径进入部署配置。
3. GDN、视觉和预处理：完善融合，减少全局中间张量、逐块 launch、FP32/BF16 转换与文件交换；按业务形状捕获和复用图。
4. MTP：减少图构建及跨卡/CPU 同步，在实际并发需要时实现跨请求批量验证，不能用串行会话数量冒充批处理收益。
5. 离线调优生成部署配置：将实验矩阵结果收敛成具体形状桶和运行配置，不持续增加未经验证的默认开关。

## 验收口径

- 固定 GPU 拓扑、驱动/运行库版本、模型内容指纹、processor/template、图片预算、输出限制和采样。
- 用同一组业务图片测试完整预处理、视觉、prefill、decode 与输出；记录 TTFT、P50/P95、吞吐、显存及业务质量。
- 分别记录冷图片/冷前缀、真实重复请求以及实际并发。双方使用同等缓存语义，并明确 KV dtype。
- 同时保留线上 vLLM 配置和调优后的 vLLM MTP 对照，不能只选择更慢的配置。
- CUDA 回归、优化前后 token 一致性及跨引擎差异分别记录；当前严格 token 比较不能被悄悄放宽。业务容差需单独由业务标准定义。
- 最近已测的原生约 2.835 秒与 vLLM MTP3 约 1.949 秒只是耗时差距，输出仍不同。现有成果未达到交付目标。
